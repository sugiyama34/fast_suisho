# experiment-009: 教師データ量のアブレーション (奏乗をどこまで減らせるか)

作成: 2026-09-28 / 状態: **準備のみ・学習未着手** (学習は新サーバーで開始する。§7 引き継ぎ参照)
レポート期限: 2026-10-02 (金)

## 1. 仮説 (ユーザー)

- 評価関数は小さい NNUE (SFNN_halfka2_1024-7-64) なのに、教師 (奏乗 146.7 億局面) は巨大
- したがって教師は過剰で、**削減したサブセットでも水匠 11 と同等の強さに届く**のではないか
- 同一ハイパーパラメータで 100% / 90% / 80% / 70% / 50% / 30% / 10% を比較する

## 2. 事前の見立てと交絡

- **見立て (Claude)**: FT 層の重みは疎にしか更新されない (ある玉位置×駒位置の重みは、その特徴を
  含む局面からしか学習しない)。削減すると稀な特徴の重みから先に劣化するので、50% 程度までは
  小さな損失、10% では大きな損失を予想する。10% 削減の差は対局の信頼区間 (±20〜30 Elo) に
  埋もれる可能性が高い
- **交絡: 周回数**。BulletOu は総局面数 (sb × 40M × epoch) で止まり、教師ストリームは EOF で
  先頭に wrap する。同一ハイパーパラメータではサブセットが小さいほど同じデータを多く周回する。
  experiment-006 で「4〜5 周がピーク、9.4 周で −160 Elo」の過周回劣化を観測済み (LR 周期に
  よらない)。このままでは「データが減った効果」と「周回しすぎの効果」を区別できない
- **対策 (追加学習なし)**: LR は epoch 境界で warm restart するので、各 epoch 末の checkpoint は
  すべて LR 最小点で比較可能。各 arm について 2 点を評価する
  - **最終 checkpoint** (同一レシピ = 同一ステップ数): 「今のレシピのままデータを減らせるか」
  - **周回数を full に揃えた checkpoint**: 「データそのものが冗長か」

## 4. サブセット (`subsets.py`)

奏乗 30 ファイルを 10 サブスタックに分ける。S_d = ファイル番号の 1 の位が d の 3 ファイル
(S_1 = {001, 011, 021}, …, S_0 = {010, 020, 030})。ファイル内・間の並び順 (生成時刻順か等) は
文書化されていないため、連番の塊ではなく 001〜030 全域にまたがる取り方にした。

| Stage | arm | サブスタック | ファイル数 | 局面数 |
| --- | --- | --- | --- | --- |
| 1 | `full` | 全部 | 30 | 146.7 億 |
| 1 | `full-rot` | 全部 (016 始まりに回転。ノイズ床の推定用) | 30 | 146.7 億 |
| 1 | `p50` | S1 S6 S3 S8 S4 | 15 | 73.3 億 |
| 1 | `p30` | S1 S6 S3 | 9 | 44.0 億 |
| 1 | `p10` | S1 | 3 | 14.7 億 |
| 2 | `p90-d{0,3,6}` | S_d を 1 つ落とす | 27 | 132.0 億 |
| 2 | `p80-d{0,3,6}` | 連続 2 つ落とす (d, d+1) | 24 | 117.4 億 |
| 2 | `p70-d{0,3,6}` | 連続 3 つ落とす (d, d+1, d+2) | 21 | 102.7 億 |

- Stage 1 はネスト (p10 ⊂ p30 ⊂ p50 ⊂ full)。取得順もこの順 (`SOJO_ORDER`, `scripts/fetch_teacher.sh`)
  にすれば小さいサブセットから学習を始められる
- 学習時のファイル順は常にファイル番号の昇順 (`full-rot` のみ回転)。BulletOu は学習時に
  再シャッフルしない。初期化シードも固定なので、同一 arm の再実行は (GPU の非決定性を除き)
  同じ結果になる。反復の代わりに `full-rot` をノイズ床とする
- Stage 2 はユーザー案の「10 パターン」ではなく 3 パターンずつ。3 パターンの差がノイズ床を
  明確に超えたときだけ残りを追加する

## 5. 学習レシピ (全 arm 共通, `run_training.sh`)

- BulletOu `2a8e5ed` + `bulletou-multiarch.patch` (sm_80 / sm_90 / sm_120 の SASS を埋め込む。
  experiment-005 の `bulletou-sm120.patch` は sm_120 専用で A100 では動かないため置き換え)
- `--arch SFNN_halfka2_1024_7_64_k3k3 --positions-per-superbatch 40000000 --superbatches 108`
  `--lr 0.000875 --lr-min 0.000030 --lr-schedule step --optimizer ranger --optimizer-weight-decay 0.0`
  (experiment-006 と同一。loss は既定の sigmoid-MSE, lambda 1.0, scale 290, batch 65536)
- 検証: floodgate.hcpe 30 万局面を 4 sb ごと。`--test-seed 20260928` で毎回同じ局面を使う
  (arm 間・epoch 間で test loss を直接比べるため)
- `--save-rate 9999` + 既定の epoch 末保存 → checkpoint `NNNN` = epoch 番号。1 個 2.3 GB
  (nn.bin 135 MB + state.bin 2.2 GB)。20 epoch × 14 arm で約 650 GB
- epoch 数の既定は 20 (864 億局面, experiment-006 の yane20 と同じ)。**計算資源が足りなければ
  全 arm で同じ値に下げる**。`--max-epochs` は resume シグネチャに含まれないので、止めた run を
  後から大きい値で再開して延長できる
- 早期終了: 「epoch 末 validation が改善しなければ停止」は plateau スケジュール専用で、step
  スケジュールでは発動しない (ソース `examples/bulletou.rs` で確認済み)。全 arm が同じステップ数を学習する

周回数 (epoch 数 E のとき, 1 epoch = 43.2 億局面):

| full | 5.9 | 20 |
| p90 | 6.5 | 18 |
| p80 | 7.4 | 16 |
| p70 | 8.4 | 14 |
| p50 | 11.8 | 10 |
| p30 | 19.6 | 6 |

## 6. 評価

- **対局 (`match_nodes.py`)**: 固定ノード数 (`go nodes N`)、各エンジン Threads 1 (探索が決定的)、
  W 組のエンジンペアを並列。開始局面は互角局面集 ply24 (30,053 局面) から等間隔に `--pairs` 個、
  **全 arm で同じ局面集合**を使う。1 ペア = 先後入替 2 局、pentanomial で Elo と 95% CI。
  対局ルールと統計は experiment-005 の実装 (`match_runner.play_game`, `match_sprt`) を再利用
- 相手: 水匠 11 (`~/suisho11/nn.bin`)。FV_SCALE は両陣営とも既定 16 (experiment-006 と同じ)。
  全 arm が同一レシピなので FV_SCALE のずれは全 arm に共通にかかり、arm 間比較には効かないが、
  水匠 11 との絶対差はずれうる (`docs/TRAINING.md` 知見 3)
- ノード数 N は未決定。新サーバーで 1 局あたりの時間を測ってから決め、全対局で固定する。
  目安: 旧プロトコルは 1 手 約 2M ノード (16 スレッド)。500 ペアで CI 約 ±30 Elo
- 評価する checkpoint: 各 arm の最終 epoch と §5 表の「周回数を揃えた epoch」。
  Stage 2 の近接 arm は full arm との直接対局も行う
- 副指標: floodgate test loss / accuracy の epoch 曲線 (W&B)。accuracy は強さの代理にならない
  (experiment-006) ので決定には使わない
- **未検証**: `match_nodes.py` と `train_supervised.py` は ruff を通しただけで、実行はしていない。
  最初に数ペアの smoke 対局と `SMOKE=1` の学習で動作確認すること

W&B: `train_supervised.py` がトレーナと run のライフサイクルを一体で管理し、
`summary-learn.log` の行と `passes` (周回数) を送る。`WANDB_API_KEY` がプロセス環境に無いときは
offline で記録するので、後でキーを持つ端末から `uv run wandb sync wandb/offline-run-*` で送る。
キーはリポジトリにも `~/.claude/settings.json` にも書かない (ユーザー方針)。渡し方は
`docs/SETUP.md` §1。

## 7. 計算量見積もりと引き継ぎ

### kajiki (旧: 2026-09-28 のサーバー) での実測

GPU は RTX PRO 6000 Blackwell を MIG 1g.24gb ×4 に分割したもので、使えるのは 2 スライスだけ
(他ユーザーと共用)。教師 2300 万局面をページキャッシュに載せ、ディスクの影響を除いて測った:

| 構成 | 1 sb (4000 万局面) の実時間 | 1 run の速度 |
| --- | --- | --- |
| 1 run 単独 (loader 8 スレッド) | 57〜60 秒 | 0.71M 局面/秒 |
| 2 run (1 スライス 1 run) | 62〜63 秒 | 0.64M 局面/秒 |
| 4 run (1 スライス 2 run) | 133〜139 秒 | 0.29〜0.30M 局面/秒 (合計は増えない) |

- スライスあたり約 0.65M 局面/秒で頭打ち = **MIG スライスの GPU 律速**。864 億局面の 1 run に
  約 37 時間かかり、Stage 1 だけで期限を超えるため新サーバーへ移ることにした
- 進捗行の `pos/s` (約 4.2M) は GPU へのカーネル投入時間しか数えておらず、実時間の速度ではない。
  **速度は進捗行の間隔 (実時間) で測る**
- glibc malloc の調整 (huge page, mmap 無効) は効果なし。ページフォールトは消えたが速度は同じ

## 8. experiment-010 (定跡局面の除外) の準備メモ

- 狙い: 定跡に現れる局面を教師から除いたとき、その局面の評価がどれだけ悪化するか。
  対照は「同数の非定跡局面をランダムに除外」。除外局面は全体の 0.03% 程度なので対局では
  差が見えない。**主指標は除外局面上の held-out loss** (教師評価値との誤差)、対局は副指標
- 局面の照合: cshogi の 32 バイト PackedSfen は手数を含まず、同一局面なら経路によらず
  同じバイト列になる (2026-09-28 確認)。教師レコード先頭 32 バイトのバイト一致で照合でき、
  147 億レコードをデコードせずに済む
- 定跡の候補:

| 定跡 | 局面数 | ライセンス | 備考 |
| --- | --- | --- | --- |
| 新ペタショック定跡 (やねうら王, 2025-05) | 約 233 万 | MIT | 第一候補。YaneuraOu DB2016 テキスト形式 (`sfen` 行)。**先手番の局面だけ**を持つので、後手番の教師局面は盤面を 180 度回転・先後反転してから照合する。手数欄は常に 0 |
| 700T-shock-book (やねうら王, 2019) | 約 28.5 万 | 明記なし | 両手番・手数あり。小さく試しやすい |
| 互角局面集 2025 ply24 + ply32 | 約 5.6 万 | MIT | 定跡木ではなく 2 手数の断面。ライセンス必須のときの代替 |

  配布元 URL: 新ペタショック定跡は YaneuraOu の GitHub release `new_petabook233`、
  700T は release `BOOK-700T-Shock`
- 最初に教師 1 ファイルで各候補のヒット数を数えてから本番の除外に進む

## 対局 (`match_nodes.py`, 2026-09-29)

- smoke: 水匠 11 同士、10k / 30k ノードでエラーなし
- **固定ノード + Threads 1 の対局は完全に決定的**: 並列数 W やワーカーの割り当て、ビルド (AVX2 / ZEN3)
  を変えても 16 局すべて同一。ハーネスが毎局 `isready` を送り、置換表と探索履歴が消えるため。
  同じエンジン同士では先後を入れ替えても同じ棋譜になる (同一ネット同士の対局は 1 局面 1 棋譜)
- 変更: `match_runner.play_game` に指し手の出力 (`moves_out`) を追加。`match_nodes.py` は各局に
  `moves` と `sec` を記録し、再開時に開始局面が一致しなければ停止する (`--pairs` を変えて再開すると
  局面の等間隔抽出がずれるため)
- 速度 (Threads 1, W=16, GPU 計測と同時):

| ノード数/手 | 局数 | 平均 秒/局 | 秒/手 | 平均手数 | W=48 での推定 ペア/時 |
| --- | --- | --- | --- | --- | --- |
| 100k | 64 | 15.4 | 0.120 | 128 | 約 5,600 |
| 300k | 64 | 42.1 | 0.347 | 121 | 約 2,050 |
| 1M | 32 | 171.6 | 1.200 | 143 | 約 500 |
| 2M (推定) | – | 約 320 | – | – | 約 270 |

- 1 ペア = 1 コア程度。学習中は BulletOu のローダ (1 run 8 スレッド) と合わせて 64 コアを超えないよう
  W ≈ 32〜40 にする
- ワーカーあたりの局数が少ないと最も遅い局で全体が決まる (1M: 理想 343 秒に対し 733 秒)

### スクリプト (`stress/`)

実行時の状態 (pid ファイル・ログ・学習と対局の出力・記録) はすべて `/mnt/nvme1/sugiyama/stress/` に置く。
experiment-009 の checkpoint と棋譜、`notes/ratings.md` には触れない。

| スクリプト | 内容 |
| --- | --- |
| `gpu_load.sh <gpu>...` | GPU 1 枚に学習 1 本 (`run_training.sh` と同じ引数, arm p10, 止めるまで続く)。名前は `g<gpu>` |
| `cpu_load.sh <W> <name>` | 水匠 11 同士 300k ノード・Threads 1 を W 並列 (`match_nodes.py`, nice 10)。名前は `c1`, `c2`, … |
| `stop.sh <name>...` | 指定した負荷を止める (SIGTERM → 5 秒後に SIGKILL) |
| `stop.sh` | **緊急停止**: 全負荷を即座に SIGKILL (取りこぼしの bulletou・やねうら王も PID で止める) |
| `monitor.py` | GPU の電力・使用率・温度・クロック, CPU 使用率・Tctl・クロック, 動いている負荷を 5 秒ごとに CSV と .txt へ |

- 各負荷は新しいセッションで起動し、プロセスグループ ID を `pids/<name>.pid` に書く (boot_id 付き。
  落ちて再起動したあとの古い pid ファイルは無視する)。開始・停止は `events.log` に時刻付きで残る
- `DRY_RUN=1` で起動するコマンドを表示するだけにできる
- 学習は 1 epoch (約 63 分) ごとに checkpoint (約 2.3 GB) を `stress/gpu/g<N>/` に書く。その前後に短い GPU の谷が出る

### 手順 (案)

各段の保持時間は、GPU は使用率が 100% になってから数える (起動から約 1 分)。

| 段 | コマンド (`S=experiments/009-data-scaling/stress`) | 負荷の合計 | 保持 |
| --- | --- | --- | --- |
| 0 | `python3 $S/monitor.py` (tmux) | アイドル | 3 分 |
| 1 | `bash $S/gpu_load.sh 0` | GPU 1 枚 | 3 分 |
| 2 | `bash $S/gpu_load.sh 1` | GPU 2 枚 | 3 分 |
| 3 | `bash $S/gpu_load.sh 3` | GPU 3 枚 | 3 分 |
| 4 | `bash $S/gpu_load.sh 2` | GPU 4 枚 | 3 分 |
| 5 | `bash $S/gpu_load.sh 4` | GPU 5 枚 (10-01 に 10.5 時間持った構成) | 5 分 |
| 6 | `bash $S/cpu_load.sh 16 c1` | GPU 5 枚 + 対局 16 | 5 分 |
| 7 | `bash $S/cpu_load.sh 16 c2` | GPU 5 枚 + 対局 32 (**09-29 に落ちた構成**) | 10 分 |
| 8 | `bash $S/cpu_load.sh 16 c3` | GPU 5 枚 + 対局 48 (CPU 64 コアはほぼ飽和) | 5 分 |
| 9 | `bash $S/cpu_load.sh 16 c4` | GPU 5 枚 + 対局 64 (全負荷) | 30 分 (管理者の判断で延長) |
| 10 | `bash $S/stop.sh` | アイドルに戻す | 3 分 |

- 合計 約 75 分。GPU を先に上げるのは、GPU 5 枚だけの構成が実績のある安全な状態で、限界に近い後半を
  刻みの細かい CPU (16 コアずつ) で上げるため
- 学習 5 本のローダで CPU は約 15〜20 コア使うので、対局 48 並列あたりで 64 コアが飽和する
  (c4 で CPU の電力はほとんど増えない見込み)
- 学習は GPU の電力上限に届かない (約 200〜260 W/枚 対 上限 250〜300 W)。最悪の場合の GPU 電力ではない
- 途中で危ないと判断したら `bash $S/stop.sh` (全停止) か、直前に足した負荷だけ `bash $S/stop.sh c2` など

### 運用上の結論

- GPU と CPU を併用するときは従来どおり **GPU 3 枚 + CPU 32 コアまで** (実績あり)。GPU 5 枚のときは対局を動かさない
  (学習 5 本のローダ 約 15 コアのみで 10.5 時間の実績)
- GPU 5 枚 + 対局 16 並列は未確認。使うなら管理者と相談のうえ長時間の試験が要る
